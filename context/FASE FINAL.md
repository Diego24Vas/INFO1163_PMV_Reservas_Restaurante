# **¿QUÉ ES EL PMV?**

Corresponde a la **primera versión funcional** de la aplicación empresarial desarrollada por el grupo

**No espero una aplicación completa, perfecta ni equivalente a un sistema comercial real**. Lo que si espero es que cada grupo logre una aplicación que permita ejecutar procesos reales, posea funciona- miento coherente, tenga persistencia de datos, incorpore validaciones, permita navegación funcional y lo- gre demostrar valor operativo real

El PMV **NO** es una maqueta, **NO** es un conjunto de pantallas bonitas, **NO** es una presentación disfrazada de software… **el PMV debe comportarse como una aplicación real, aunque sea limitada en alcance**

El proyecto completo es una secuencia progresiva MPN → PMN → PMV, en que cada fase representa una mirada distinta sobre el mismo problema

**MPN** (Modelado del Proceso de Negocio). Aquí el objetivo fue comprender el problema, identificar actores, decisiones, estados, excepciones y flujo operacional.

**PMN** (Prototipo Mínimo Navegable). Aquí el objetivo fue imaginar y visualizar cómo se vería la solución desde el punto de vista del usuario.

**PMV** (Prototipo Mínimo Viable). **Ahora el objetivo es transformar esa idea en una aplicación real y fun- cional, aunque sea mínima**  
Espero que el PMV tenga una lógica concordante con el MPN. Premiaré en puntaje a los grupos que logren coherencia clara entre problema, modelo, navegación y funcionamiento real

El objetivo **NO** es desarrollar “todo el sistema” sino que construir una aplicación pequeña o mediana que funcione, tenga sentido, resuelva algo importante y pueda ser demostrada de forma convincente

**Un buen PMV NO es el que tiene más pantallas** sino aquel que ejecuta correctamente un proceso rele- vante, mantiene coherencia operacional y se percibe claramente que realiza procesos reales

# **CARACTERÍSTICAS QUE DEBE TENER EL PMV**

| FUNCIONALIDADES \- Espero que incorporen, de alguna forma, elementos tales como: autenticación o identificación de usuarios persistencia real de datos navegación funcional entre vistas validaciones relevantes manejo básico de errores flujo operacional coherente operaciones significativas sobre datos consistencia visual mínima separación razonable entre roles o actores simulación razonable de contexto empresarial No espero complejidad extrema, pero si exigiré funcionamiento verificable |
| :---- |
| **PERSISTENCIA Y DATOS** \- espero persistencia real, por ejemplo: bases de datos, archivos, almacena- miento local No castigaré excesivamente una solución parcialmente simulada si el funcionamiento general es cohe- rente, la aplicación demuestra valor y la simulación tiene sentido técnico. Por ejemplo, aceptaré pagos simulados, correos ficticios, datos de prueba, inventario reducido, usuarios simulados, etc. Lo importante es que la aplicación se comporte de manera creíble y consistente |
| **TECNOLOGÍAS** – pueden usar diversas tecnologías, herramientas o plataformas. Por ejemplo: React, Next.js, Flutter, Python, Flask, FastAPI, Streamlit, HTML/CSS/JavaScript, Firebase, Supabase, herramientas low-code o no-code, generadores apoyados por IA, etc. Pero, la herramienta utilizada **NO** determina la calidad del proyecto. Una aplicación técnicamente simple pero coherente y funcional puede valer más que una aplicación visualmente impresionante pero vacía. |

Pero existe una diferencia enorme entre usar IA para potenciar el desarrollo y depender completamente de ella sin comprender lo construido.

Pedir “hazme una aplicación” casi nunca produce buenos resultados reales. Los mejores resultados apa- recen cuando cuestionan, corrigen, prueban, adaptan, reestructuran y conversan técnicamente con la IA

**Hasta ahora he dejado claro que no necesitan ocultar el uso de IA, pero que deben demostrar capa- cidad para utilizarla inteligentemente**

**IMPORTANTE** – Calificaré con menos puntajes situaciones tales como…

Interfaces bonitas pero vacías, navegación falsa, CRUD irrelevantes sin sentido operacional, procesos in- coherentes, aplicaciones copiadas o apenas adaptadas, proyectos imposibles o excesivamente ambicio- sos, videos engañosos, simulaciones que no funcionan realmente, dependencia absoluta de IA sin com- prensión mínima (más funcionalidades NO significa automáticamente mejor proyecto)

**IMPORTANTE** \- Recomiendo que cada grupo seleccione unos pocos procesos importantes y los imple- mente bien. Es preferible una aplicación pequeña pero sólida que una gigantesca pero llena de partes su- perficiales (un PMV ambicioso pero incompleto vale menos que un PMV coherente y realmente funcional)

# **CRITERIOS GENERALES DE EVALUACIÓN**

**Valoraré especialmente:** funcionamiento real, coherencia operacional, comprensión del problema, cali- dad del proceso implementado, consistencia entre partes del sistema, uso inteligente de IA, claridad téc- nica, validaciones razonables, persistencia funcional, autenticidad del proyecto, capacidad de explicación del grupo, evidencias de aprendizaje real

**También valoraré el uso inteligente de IA**: la IA acelera enormemente el desarrollo, pero NO reemplaza la necesidad de pensar, probar, corregir y decidir

**Características de un buen proyecto: procesos claros, pocas funcionalidades bien implementadas, validaciones razonables, coherencia, sensación de aplicación real, buenas explicaciones, eviden- cias de iteración y mejora**
